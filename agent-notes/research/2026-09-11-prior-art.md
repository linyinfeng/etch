# Typst 生态里的 literate programming：现有工具盘点

- 日期：2026-09-11
- 问题：写一个"基于 Typst、与目标语言正交"的 literate programming 工具，前面已经有什么？我们的差异化在哪？
- 结论（TL;DR）：
  1. **"Typst + tangle" 已经被做过两次**，但都是"最小实现"：`littst`（noweb 子集的 Rust 复刻，weave 出 `.typ`）和 `typst-unlit`（Typst 文档当 GHC 预处理器，tangle 逻辑就是 `typst query | jq`）。两者都**不解决错误定位**，`typst-unlit` 自己在文末明说 "this script does clobber the line numbers, so users beware"。
  2. Typst Universe 上**没有**任何 literate/tangle 包。生态里只有两类相关包：代码排版（`codly`、`codelst`、`zebraw`）和**执行**代码块（`calepin`，notebook 路线，不是 tangle）。
  3. 最新一代通用 LP 引擎（Ravel，2026，Node）已经形成"格式适配器 → 中间表示 → 图求值 → 产物 + provenance"的分层，但**没有 Typst adapter**；它把"生成物里的偏移映射回源文档"做成了查询能力（`inspect --provenance`），方向和我们一致。
  4. AI 时代的相关工作已经出现（arXiv 2608.24644，2026-08）：把 **name 当一等对象**、维护 prose/name/artifact 的 **name-graph**，明确说这是为了让 LLM 更好地用 context window、并给 coding agent 提供类似 IDE 的符号检索。它的实现是自定义语法 + 自写 parser；我们能用 Typst label + `typst eval` 极低成本拿到同样的图。
- 所以差异化是：**(a) 单一 `.typ` 文件为唯一真相且本身可编译/可预览；(b) 不写 Typst 解析器；(c) 把"错误定位 + 生成物漂移检测"当一等公民，这是 AI agent 修 bug 时的刚需。**

## 1. 经典 / 教科书路线

| 工具 | 形态 | 对我们的启发 / 教训 |
| --- | --- | --- |
| **WEB** (Knuth 1984) | Pascal 专用，`@<name@>=` 定义 chunk，`#line` 让编译器报错指回 WEB 源 | "错误定位"从第一天就是 LP 的一部分；tangle 产物带行指令是原始设计，不是附加功能 |
| **noweb** | 语言无关的极简设计：`<<name>>=` 定义、`<<name>>` 引用、`@` 分隔文档块；`notangle`/`noweave` | 我们要的"正交"就是 noweb 的定义：**只做文本替换，不解析目标语言**。缩进语义（子 chunk 整体缩进到引用点）是必须实现的；`-L` 关掉缩进调整是给 Fortran/缩进敏感语言留的逃生口（<https://www.cs.tufts.edu/~nr/noweb/FAQ.html>） |
| **Weft**（nuweb 派） | 语言无关，250+ 语言自动识别，section marker 便于调试 | "section marker"= 生成物里带 chunk 边界标记，是错误定位的另一种做法 |
| **org-babel** | `:tangle file`、`:noweb yes`、`:noweb-ref name` 把多个 block 归到一个名字下并**按文档顺序拼接** | 拼接语义的先例；`#+PROPERTY: header-args` 全局默认值也是我们要考虑的 ergonomics（<https://orgmode.org/manual/Noweb-Reference-Syntax.html>） |
| **knitr / R Markdown** | 可执行 chunk + `purl()` 抽取代码 | 验证了"文档为真相"在数据科学里能活下来；但它是"weave 出结果"，tangle 是附属 |
| **literate Haskell / Agda** | `.lhs`、`.lagda.md`、**`.lagda.typ`**（Agda 原生支持 Typst！） | 官方语言原生支持 literate 的分界线是"注释 vs 代码哪个是一等公民"；Agda 已经证明 `.typ` 可以当 literate 载体（<https://agda.readthedocs.io/en/v2.8.0/tools/literate-programming.html>） |
| **markdown-unlit / unlit** | GHC 的 `-pgmL` 自定义预处理器机制 | 让语言自己的构建系统调用我们的 tangle，是"零侵入"集成路径 |
| **Literate Tracing**（arXiv 2510.09073） | 用真实执行 trace 串起文档 | 提醒：literate 文档的"骨架"未必是 chunk 依赖图，也可以是执行轨迹 |

## 2. Typst 相关的现有实现（最需要直视的）

### littst — <https://github.com/js216/littst>
- 形态：两个短 Rust 程序。`tangle` 从 noweb 风格 `.nw` 抽源码；`weave` 把 `.nw` 转成 `.typ`，再由 typst 编译。
- 关键设计：文档正文**本来就是 Typst 语法**（`= 标题`、`== 小节`），weave 几乎是恒等变换；代码块按"以 `.` 结尾的 chunk 名"推断语言（`main.c` → `c`），语言从根 chunk 沿引用图传播。
- 教训 / 我们不会照抄的地方（读源码得出）：
  - 缺失引用的 chunk **被静默丢弃**（`expand` 里 `if let Some(target)` 没有 else），必须报错。
  - weave 对每一行代码输出一个 `#raw(lang:..., "...")` + `#h(1em)`，丢了块的语义、也没法用 codly 之类的包。
  - chunk 锚点用 `DefaultHasher` 哈希（`chunk-<hex>`），不可读、且 Rust 不保证跨版本稳定。
  - 无行号映射、无 watch、无重复 chunk 追加语义。

### typst-unlit — <https://tangled.org/@oppi.li/typst-unlit>
- 形态：**同一个 `.lhs` 文件既是 Haskell 源（经 GHC `-pgmL` 预处理）又是 Typst 文档**；unlit 本身用 Haskell 写，且**用 Typst 渲染自己**。
- 核心机制（文末 shell 等价物，值得照抄的极简形态）：
  ```sh
  typst query "$3" 'raw.where(lang: "haskell-top")' | jq -r '.[].text' > "$4"
  typst query "$3" 'raw.where(lang: "haskell")'     | jq -r '.[].text' >> "$4"
  ```
  即：**Typst 自己就是解析器**，fenced block 的 `lang` 就是 chunk 选择器。
- 它自己承认的两个问题：行号被清空（"users beware"），以及 naive 的 chunk 搬移会打乱 GHC 报错位置。Reddit 讨论里也有人指出"移动代码会破坏错误位置，这正是注释存在的理由"（<https://www.reddit.com/r/haskell/comments/1oqsf03/>）。
- 教训：**用 `lang` 当 chunk 选择器会和"语言标签只用于高亮"冲突**（一个文档里同一语言的 chunk 无法分别命名）。我们改用 `label` 当名字、`lang` 只管高亮。

### Calepin — <https://typst.app/universe/package/calepin/>
- 形态：Typst 包 + 执行器。扫描 `.typ` 里的 raw block 和 inline code，按语言调用 Python/R/Julia/shell/Mermaid/DOT/TikZ/D2 引擎，**把执行结果注入回原位**，编译时完成。
- 是"计算型 notebook"，不是 LP：没有 chunk 组合、没有 tangle、没有多文件产物。
- 但它证明了：`.typ` 里扫描代码块的路线在 Typst 生态里是可接受、可发布的（另一个"Typst 当解析器"的先例）。
- 相关排版包：`codly`（行号/高亮/跳行/语言图标）、`codelst`（行号 + 引用源码行范围）、`zebraw`。我们的 weave 库应该和它们共存而不是重造；注意 `show raw.where(block: true)` 的规则会和 codly 冲突，需要明确的组合策略（见 design-space）。

## 3. 新一代通用引擎

### Entangled — <https://entangled.github.io/>（2023 论文 DOI 10.1109/e-science58273.2023.10254816）
- 双向 tangle daemon：Markdown/Org/noweb 为源，监听文件系统，文档改动写源码、源码改动写回文档；用 SQLite 存状态；Pandoc filter 负责 weave；支持 line directives。
- 教训：双向同步是它最大的卖点也是最大的复杂度来源（冲突消解、错误编辑的鲁棒性）。**我们的第一版应该是单向（`.typ` → 源码）**，把双向留作明确的可选后端。

### Ravel（2026，Node）— <https://github.com/jostylr/ravel>，<https://ravel.jostylr.com>
- 明确分层：`Markdown/MyST/Org/noweb/AsciiDoc/HTML → Ravel Map（版本化中间表示）→ chunk parser + graph evaluator → Ravel Program → deliverables/diagnostics/provenance/trace`。格式策略与组合逻辑解耦，适配器是可独立发布的 npm 包。
- 已有能力（值得抄的清单）：source-ranged chunk、chunk 地址（local/global/cross-document/typed）、`emit` 派生 chunk、定义期/使用期 transform、命名输出计划、**provenance 查询**（`inspect --provenance dist/greeting.js --generated-offset 0`）、路径逃逸防护、QuickJS 沙箱内跑 JS chunk。
- **没有 Typst adapter**。它的 `markdown-litpro` 适配器有 `#lp-name` 之类的属性语法，说明"fence info string 里塞属性"是通用做法。
- 教训：中间表示 + provenance 是成熟形态；我们不一定要做完整 IR，但"生成物偏移 → 源文档位置"必须是可查询的一等数据。

### 其他同类（未细读，列名备查）

## 4. AI 时代的相关工作

| 工作 | 要点 | 与我们的关系 |
| --- | --- | --- |
| **A Literate Programming Environment for Human and Machine Agents**（arXiv 2608.24644, 2026-08-25） | 可执行 program essay 的语法；parser 把 **name 当一等对象**；内部 **name-graph** 关联 prose/name/artifact；给出 3 种语言的 binding；明确动机是"更好利用 LLM 的 context window""给 agent 提供类似 IDE 符号检索的工具" | 最接近我们论点的学术工作。它自建语法 + 自写解析器；**我们用 Typst 文档 + label + `typst eval` JSON 就能生成同构的 name-graph**（区别是我们把解析、渲染、预览都外包给 Typst） |
| **Literate Programming With LLMs?**（IEEE TSE 52(2), 2026-02） | 在 Rosetta Code / CodeNet 上做实验研究 | 提供"LLM 时代 LP 有用"的实证背景；需要精读其结论再引用 |
| **llp — Linked Literate Programming**（<https://github.com/ccheever/llp>） | 口号即设计："Keep humans in markdown. Let AI write and review the code." 人写 prose/设计/取舍，AI 写代码 | 代表了"人机分工"的另一种主张：人类层用 Markdown。我们要论证 `.typ` 比 Markdown 更适合这一层（排版即产物、可直接预览） |
| **litprog-skill**（<https://github.com/tlehman/litprog-skill>） | Claude Code / OpenCode 技能：**把已有代码库反向转成 literate program** | 反方向（code → doc）的工具化先例，说明 agent 场景下"生成文档"这一侧已经有人在做 |
| 综述文：Revisiting Literate Programming in the Age of AI Agents | 论点：agent 消灭了 LP 的传统维护负担 | 我们的动机叙述可直接引用；注意它没有给工具实现 |

## 5. 历史包袱：LP 为什么没普及（决定了我们的设计重点）
1. **维护负担**：文档和代码两份真相 → 漂移。Entangled 用双向同步解，我们用 `--check` + CI 解。
2. **工具链摩擦**：编辑器不会高亮、没有跳转、报错定位不到源。Typst 这边反而占便宜：`.typ` 本身有 typst-lsp / typst-preview 实时预览，写代码块时就是普通 fenced block。
3. **代码二等公民**：写 LP 后不能用 IDE 重构。缓解手段是让 chunk 名 = 符号（name-as-first-class），把重构问题变成重命名 chunk 名。
4. **读者错位**：LP 的读者往往是作者自己；AI 时代读者多了一个 agent，而 agent **恰好更喜欢连贯的自然语言上下文**——这是本项目最重要的新论据。

## 6. 现有实现的问题清单（我们的机会）
- 没有工具把"tangled 文件第 N 行"映射回"`.typ` 第 M 行"（littst/typst-unlit 都没有）。
- 没有工具能检测生成物漂移并以非零码退出（CI 用）。
- 没有工具支持"同一 chunk 名多块拼接 + 显式报错"的完整 noweb 语义（littst 有拼接但会静默丢引用）。
- 没有 Typst 版的 provenance/name-graph 查询（Ravel 有，但没有 Typst adapter）。
- 没有工具把"文档正文就是最终排版源"和"chunk 组合"同时做到：littst 需要 `.nw` 预处理才能编译，Calepin 不做组合。
