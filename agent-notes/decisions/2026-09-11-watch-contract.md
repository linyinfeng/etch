# 实时同步的行为契约（watch）（2026-09-11）

`lazy-tangle` 分支合入 main 时把 `lp watch` 的三条语义固定下来。它们不是"实现细节"，而是**用户和其它工具（cargo、rust-analyzer、编辑器）依赖的契约**——任何一条被破坏都会表现为"莫名其妙的重建/诊断噪音"，所以写成 ADR。

数据依据：`../research/2026-09-11-lazy-tangle.md`（2201 行 / 200 根 chunk：全量 7ms、无变化 3ms、改一个 fragment 只重写 1 个文件）。

---

## D9 — 实时同步：只写变化、拒绝半写、事件合并

- **决定**：
  1. **只写字节变化的输出。** 一轮同步比较"展开结果 vs 磁盘内容"，相同就不写（mtime 不动）。**不变式：生成物的 mtime 只在内容真的变化时改变**，这样 cargo / rust-analyzer 不会因为无实质变化的一轮而醒来。
     `.lpmap.json` 同理，但比较的是**它自己的内容**而不是输出文件：行号映射取决于文档（插入一行散文会平移所有映射）而与输出字节无关，用“输出没变”去跳过写 map 是错的（2026-09-11 修：`write_if_changed` + 回归测试）。
  2. **语法错误不 tangle。** 文档存在解析错误时，打印诊断（来自 `SyntaxNode::errors_and_warnings()`，权威来源）、跳过本轮、**保留上一份好产物**。绝不在半写状态下用"看起来还行"的 chunk 结构去覆盖输出。
  3. **事件合并。** debouncer 时间窗（默认 200ms）+ 每轮开始前抽干已排队事件（含自己写盘产生的事件）；监听**目录**（NonRecursive）而非文件本身，因为编辑器保存是"写临时文件 + rename"。
  4. **检查命令融合但受同一惰性约束**：`--check-cmd` 只在一轮**真的改写了文件**之后执行，输出走与 `lp explain` 相同的回译路径。
- **落选**：
  - 无脑重写全部输出（简单，但每次击键都让下游重建）。
  - 有语法错误时"尽力而为"地按已解析出的 chunk 继续 tangle（在实时场景里等于把半句话写进代码）。
  - 只监听 `.typ` 文件本身（原子 rename 会掉 watch）。
- **理由**：实时回路的价值 = 反馈延迟低 **且** 不制造噪音。前者靠"全量重算只要 3–7ms"（所以不需要增量解析/反向可达），后者靠上面四条。
- **代价/天花板**：
  - 每轮全量解析 + 全量展开（2201 行 / 200 根 = 7ms release）。到 ~10^5 行、或 watch 变成常驻服务时，才考虑 `typst-syntax::reparser` 与"只展开受影响的根"；`src/watch.rs` 顶部有 `ponytail:` 注记指向这里。
  - 正在运行的检查命令不会被新一轮打断（逐次串行执行）；如果 check 变慢，需要加"取消上一轮"的机制。
- **回归**：`tests/lazy.rs`（mtime 不变 / 只重写受影响文件 / 半写文档不 tangle / 双向 map / 未引用告警）。
