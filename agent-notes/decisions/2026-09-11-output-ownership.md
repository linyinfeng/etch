# 输出目录的所有权（`.lpignore`）（2026-09-11）

起因：用户问「删除一个文件 chunk 时会发生什么」。实测（当时的 main）：

```
tangle 两个根 → out/a.py out/b.py
删掉 <b.py> chunk 再 tangle → 只打印 "ok a.py"，out/b.py 原地不动（内容还是旧的）
lp tangle --check          → exit 0（漂移检查通过）
lp map --file b.py         → "not in the line map"
```

删掉/改名一个根 chunk 会留下孤儿文件，而残留的 `src/*.rs` 照样会被 cargo 编译。这是"生成物不入库"模型里最危险的一类漏网。

---

## D10 — 删除只由目录声明授权；map 只管行号映射

- **决定**：
  1. **所有权是目录问题，由 `.lpignore` 声明。** 某个目录里有这个文件，就表示"这个目录里的文件是 `lp` 的，除了文件里列出的那些"；该目录下任何**没有 chunk 产出且未被规则匹配**的文件会被删除。匹配规则**完全交给 `ignore` crate**（ripgrep 同源）：`WalkBuilder` 一次遍历完成全部工作——嵌套 `.lpignore`、深层覆盖浅层、`!`、`**`、`dir/`、注释、转义。不自己发现"被管理的根"，不自己实现匹配与优先级。
  2. **`.lpmap.json` 只是行号映射**：每次 pass 重写为本次产物，**不做所有权记忆**。它的职责就是"生成行 ↔ `.typ` 行"的正反双向链接（`lp map` / `lp explain`）。
  3. **没有 `.lpignore` ⇒ 什么都不删。** 连"删掉 chunk 后留下的那个文件"也不删，也不报"孤儿"：没有声明就没有授权。`lp` 不保留任何"我以前写过什么"的记录。
  4. **`--check` 永不删除**，是干跑：把声明目录里会被删的列成 `ORPHAN … (would be removed)`，非零退出。
  5. **只有两个控制文件豁免**：`.lpmap.json`（映射）与 `.lpignore`（规则本身）。其余文件——**包括点文件**——都是普通内容：想留下就写进 `.lpignore`。**没有任何 `git` 相关特例**（项目不与 git 耦合）；真要保留一个 `.git`，写 `.git/` 进规则即可。
  6. 删除文件后，**它所属的空目录链会被收起**（只收自己刚清空的那些）。
- **落选**：
  - **账本式所有权**（本次会话中途实现过并有测试）：让 `.lpmap.json` 保留"已无 chunk 产出"的条目，据此报 orphan、用 `--prune` 删除。否决理由：把"行号映射"和"所有权"两件事塞进同一个文件；而且 `--prune` 本质是"我猜这个文件是我写的"的兜底，而 `.lpignore` 已经能表达任何项目的需求（含"哪些文件不是我的"），多一层猜测没有必要。删除也随之有了唯一的、可审查的授权来源。
  - 手写"被管理目录"的发现与嵌套去重：用 `ignore` 库自己的 walk 就没这个问题，还白拿优先级语义。
  - `.git` 目录硬编码豁免：无 git 耦合；规则说了算。
  - 把匹配含义也做成 gitignore 的方向（匹配 = 交给 `lp` 管）：与需求规格相悖——"没有被 ignore 的文件，如果没有对应 chunk，就会被删除"。
- **一处必须讲清的反向（对齐 gitignore 的边界）**：**匹配语法与优先级 = gitignore，但"匹配上了"的含义相反**——git 里匹配 = 不跟踪，这里匹配 = **保护/留下**。把 `.lpignore` 当"要保留什么"的清单读就对了。
### 三类文件，只报第三类

输出目录里的每个文件恰好落在三类之一：

1. **produced** —— 某个 chunk 产出它（记在所在目录的 `.lpmap.json` 里）。内容归 `lp` 管，`--check` 守它。
2. **declared** —— `.lpignore` 说"lp 不管理它"。
3. **unaccounted** —— 都不是。没有任何东西解释它为什么在那里。

前两类各自有显而易见的位置（映射文件、ignore 文件），**只有第三类在构造上就是隐形的**，所以只有它值得工具主动报。`lp unaccounted` 列出它：只看"这一轮写过东西的目录"，目录条目不递归展开（`target/` 报成一行而不是几千个文件）。

第三类的每一行都是三选一，而只有用户知道选哪个：**让某个 chunk 产出它** / **在所在目录的 `.lpignore` 里声明** / **它是过期产物，删掉**。普通流程里 `lp tangle` 会打一行 note 指过去，而不是沉默。

由此派生出的升级路径（这才是 `.lpignore` 的"声明"价值）：清单上写着的东西里，有些其实**该被写进文档**——`flake.lock`、锁文件、清单这种"足够精确、可以被生成，又足够重要、值得被解释"的文件，正确做法是作为**附录 chunk** 收进 literate 文档，让散文解释它为什么长这样。

**落选：`lp ignored`**（把用户自己写的声明再念一遍并列出它当前覆盖的文件）。否决理由：它不提供任何用户还不知道的信息——声明就在文件里，本来就看得见；而"再确认一遍我声明过什么"不是这个工具要回答的问题。要回答的是**"我漏了什么"**：没被 chunk 管的、也没被声明的那些。所以命令是 `lp unaccounted`，不是 `lp ignored`。

### 修订（同日，用户定案）：未处置即错误，删除必须显式

上面那版把"已声明的目录"当作删除授权，扫描会**自动删掉**未被 chunk 产出也未声明的文件。用户否决了这个方向，定了更简单的规则：

1. **`--out` 整个目录都是 `lp` 的**——不是"写过东西的目录"，也不是"已声明的目录"。目录里的每个文件都必须被解释：要么某个 chunk 产出它（记在所在目录的 `.lpamap.json`），要么被 `.lpignore` 声明。
2. **解释不了就是错误**：`lp tangle` 直接失败（`--check` 同样失败），列出每个未处置的文件，并给出两条出路。**`lp` 从此再也不会自行删除任何东西**——`sweep.rs` 整个删掉了。
3. **两条出路**：① 在所在目录的 `.lpignore` 里声明它；② `lp unaccounted <doc>... --delete` 显式删掉它（`--delete` 就是那个 force）。
4. **报告必须基于当前文档**：`lp unaccounted <doc>...` 会重新展开文档来判断"什么算被产出"，而不是读磁盘上的 `.lpamap.json`——否则"刚删掉一个 chunk"这个最需要它的场景下，旧 map 仍把残留文件当成产出，报告反而是空的。（这个坑在测试里当场撞到。）
5. **展示粒度**：逐文件列出（可按名 grep/复制/粘贴进 `.lpignore`）；只有当一个子树的未处置文件超过 8 个时才压缩成一行目录名（`target/` 是一行，不是几千行）。目录本身从不"未处置"——未处置是**文件**的属性。

- **风险与缓解**：`--out .` 配一份写得太松的规则会删掉项目文件。缓解：①所有权必须逐目录显式声明（没有任何 `.lpignore` 就不删任何东西）；②只有两个控制文件豁免（不给人"点文件安全"的错觉）；③`lp tangle --check` 是干跑，先看再删。
- **影响**：`lp watch` 同样执行扫描（删完文件后照样触发 `--check-cmd`）；`.lpmap.json` 的语义回到"当前产物"。
- **回归**：`tests/owned.rs` 8 个用例——删除根 chunk（文件与空目录一起消失，被匹配的文件全部存活）；`dir/` 与 `**` 生效；**深层 `.lpignore` 覆盖浅层且 `!` 能把文件从保护集里拿回来**；控制文件豁免而普通点文件照规则处理；**没有声明就什么都不删（连孤儿也不删）**；`.git` 是普通内容（列了才留）；嵌套声明的作用域；`--check` 干跑。
