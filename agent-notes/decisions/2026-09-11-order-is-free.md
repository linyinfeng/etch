# D18 — 顺序自由：撤销 D16 的两条检查（2026-09-11）

用户推翻 D16，原话：

> 不不不，不需要先命名后展开，我们完全可以先描述一个重要的思想，形成一些代码片段，然后最后再简单组装起来；第二，语言一致，不要检查，这个检查不了。

## 决定

**1. 撤销"先命名后展开"（D16.1）。** 声明顺序完全自由：

- *骨架在前*：先给文件骨架，再逐节填——读者第一页就知道形状。
- *碎片在前、组装在后*：按"值得解释的顺序"把想法和片段写出来，最后用一个短节把它们组装成文件。
两者都是正当的写法，由**论证**决定用哪个，工具不投票。`lp metadata` / `lp list` 仍然按读取顺序打印声明流，需要看结构时看它们即可。

**2. 撤销"lang 一致"检查（D16.2）。** fence 上的 tag 是**数据**（高亮、映射里的语言字段），不是关于文本是什么的断言；一个片段被不同 lang 的文件引用是合法用法。这个检查本来就会产生假阳性，且它在语义上无意义——**检查不了，就不要检查**。

## 为什么会推错

D16 把"渐进式披露"当成了**声明顺序的函数**，于是可以机械判定——但它其实只在**散文层面**成立：读者能不能顺着读下去，取决于每节说了什么、承诺了什么，而不是 `.typ` 文件里 `#file` 与 `#chunk` 的先后。把结构顺序当成判据，是用一个可测的代理去代替真正的性质（古德哈特定律那一类错误），而且它会禁止一种完全正当的写法（先讲清楚、最后组装）。

工具能强制的仍然只有**机制**：引用可解析、无环、非空、产出与文本一致（`--check`）、输出目录被解释（D10）。"重思路、渐进式披露、逻辑自洽"这三件事全部落在**写作者**身上——也就是 skill 那半边。

## 保留了的东西

- **D17 转义 `@<<name>>` 保留**：它与顺序无关，是"文档引用自身语法"所必需的（skill 在 `self.typ` 里）。
- **`examples/demo/literate.typ` 的骨架式重排保留**（但改写了那句"工具只接受这一种顺序"）：它是两种正当风格中的一种，现在的demo 用它，并且在文里说明这是选择。
- `tests/metadata.rs` 的 `#for` fixture 重排保留（顺序本无意义，不必再动）。

## 验证

```sh
nix develop -c cargo test                                  # 49（撤销了那两条用例）
nix develop -c ./target/debug/lp tangle self.typ --out . --check
nix develop -c examples/demo/run.sh
```

## 影响

- `AGENTS.md` / `README.md` / handoff / plan / skill 里"结构强制"的措辞全部改掉：工具管机制，人管论证。
- 教训写进 handoff：**别把不可判定的性质换成可判定的代理然后当成同一条规则**；上一个这样想的是 D16。
